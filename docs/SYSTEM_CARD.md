> **Project:** Yami - AI-Powered Security Gate for IaC, CI/CD, and Supply Chain
> **Theme:** Track 1 - Autonomous DevOps (AI-Powered CI/CD)
> **Version:** 1.1
> **Date:** 2026-08-22
> **Status:** Active. Reconciled against implementation as of commit `5fb2515` — see §2.3 for the one known open gap between designed and enforced controls.

---

## 1. Purpose and Scope

### 1.1 Intended Use

Yami is an **AI-assisted security remediation gate** for Infrastructure-as-Code (IaC), CI/CD pipelines, and software supply chains. It operates as a GitHub Action that:

1. Scans pull requests for security vulnerabilities (Checkov, CicdRules, Trivy)
2. Evaluates findings using OWASP-aligned AI agents (Judge)
3. Produces remediation patches (Surgeon)
4. Verifies patches deterministically (Java Verifier)
5. Publishes remediation PRs (Publisher)
6. Generates tamper-evident audit trails (Auditor + Java AuditStore)

### 1.2 Target Users

- DevOps engineers reviewing infrastructure PRs
- Security engineers auditing CI/CD pipelines
- Platform teams managing golden paths

### 1.3 Non-Goals and Prohibited Uses

| Non-Goal | Rationale |
|---|---|
| **Auto-merge** | Yami never merges its own PRs. Human approval is mandatory. |
| **Production deployment decisions** | Yami remediates code, not deployment state. |
| **Data classification or PII handling** | Yami does not process user data or PII. |
| **General-purpose coding assistant** | Yami is scoped to security remediation only. |
| **Modification of governance artifacts** | Agents cannot edit `.opencode/agents/*.md` or `policies/*.yml`. |

## 2. Risk Classification

### 2.1 Risk Level: **Medium**

Yami is classified as **medium risk** per the NIST AI Risk Management Framework because:

- The AI writes code (remediation patches), which could introduce vulnerabilities if incorrect
- The AI reads untrusted repository content (potential prompt injection)
- The system has autonomous execution capabilities (PR creation)
- The per-invocation permission-scoping layer is not yet fully proven end-to-end (§2.3)
- **However:** Multiple deterministic controls that do not depend on that layer — constitutional veto, verification gate, no-merge — prevent unilateral AI action from reaching production unreviewed

### 2.2 Risk-Based Controls

| Risk | Control | Layer |
|---|---|---|
| AI writes vulnerable code | **Verifier** (terraform fmt/validate + re-scan) | Post-Surgeon |
| AI is manipulated by repo content | **Constitutional veto** (Java, pre-Judge) + LLM01 inoculation | Pre-Judge |
| AI creates unauthorized PRs | **Scoped token** (`contents:write` + `pull_requests:write` only) | GitHub Actions |
| AI exceeds budget | **TokenBudget** (1M tokens) → **KillSwitch** | Runtime |
| AI modifies wrong file | **OPENCODE_PERMISSION** (single file only) — *designed, not yet functionally enforced by OpenCode's runtime; see §2.3* | Per-invocation |
| AI merges without approval | **Branch protection** + no merge permission | GitHub platform |

### 2.3 Known Gap: Permission Scoping vs. Verification Gate

Live testing against real Bedrock (this session) found that OpenCode's own per-invocation permission engine does not yet enforce the "Surgeon edits only the target file" control end-to-end — the persistent `opencode serve` process currently runs inside the scanned repo directory (a workaround for an `external_directory` hang), and the `{{scoped_dirs}}`/`{{target_file}}` template placeholders in the agent frontmatter are never substituted. Full detail and evidence: [`docs/THREAT_MODEL.md` §3.1](THREAT_MODEL.md#31-known-gap-per-invocation-permission-scoping-is-not-yet-enforced), tracked as [issue #4](https://github.com/George-Fam/DevOps-for-GenAI---Ottawa-2026---Team-07/issues/4) (P0).

This does **not** mean an unreviewed bad patch can reach production: the risk is caught downstream by controls that don't depend on OpenCode's permission engine — the deterministic **Verifier** (re-scan + `terraform validate`/`actionlint`) rejects any patch that breaks syntax or introduces a new HIGH/CRITICAL finding, and the **Publisher never has merge permission**, so a human always makes the final call. What's unproven is the *scoping* layer specifically, not the overall no-unreviewed-merge guarantee.

## 3. Data Governance

### 3.1 Data Sources

| Data Type | Source | Sensitivity | Retention |
|---|---|---|---|
| IaC files (`.tf`, `.yml`) | Target repository | Low (infrastructure code) | Session only |
| Scanner findings (Checkov, Trivy) | Generated by Yami | Low (public rules) | Audit trail |
| OWASP skills (`.md`) | Yami repository | Low (public frameworks) | Versioned |
| Audit sessions | OpenCode exports | Low (execution trace) | Artifact per run |
| GitHub tokens | `GITHUB_TOKEN` env var | **High** | Ephemeral (runner lifetime) |

### 3.2 Data Handling

- **No PII is processed.** Yami operates on infrastructure code and public security rules.
- **Repository content is treated as untrusted data**, never as instructions (LLM01 directive).
- **Audit trails are hash-chained** (`AuditStore.java`) and published as GitHub Actions artifacts.
- **No data leaves the container** except via:
  - GitHub API (PRs, comments)
  - Amazon Bedrock API (agent invocations)
  - GitHub artifact upload (`audit.json`)

### 3.3 Data Minimization

- **Three scopes** limit data exposure:
  1. **Scan scope:** Only paths declared in `policies/yami.yml` (e.g., `**/*.tf`, `.github/workflows/**`)
  2. **Read scope:** Judge reads only directories containing findings
  3. **Write scope:** Surgeon edits only the single target file

## 4. Human Oversight

### 4.1 Four-Layer Oversight Model

| Layer | Actor | Action | When |
|---|---|---|---|
| **1. Constitutional Veto** | Java `PolicyEngine` | BLOCK | PPE, secrets, exfiltration patterns detected |
| **2. Judge Decision** | AI Judge | HUMAN_REVIEW | Context uncertain, public website signal, multi-resource |
| **3. Verification Gate** | Java `Verifier` | Escalate | Patch fails `terraform validate`, re-scan finds new issues |
| **4. PR Approval** | Human reviewer | Accept/Refuse | Final gate before merge |

### 4.2 Escalation Path

```
Finding detected
    → Constitutional veto? → BLOCK → Human review required
    → Judge decides HUMAN_REVIEW? → Comment on PR → Human decides
    → Judge decides SAFE_FIX
        → Surgeon applies patch
        → Verifier checks
            → FAIL? → Escalate to human with trace
            → PASS? → PR opened
                → Human accepts or refuses
```

### 4.3 Override and Appeal

- Any `BLOCK` or `HUMAN_REVIEW` decision includes a detailed reason in the PR comment
- The audit trail (`audit.json`) contains the full context for human review
- Humans can always override Yami by merging or closing the PR manually

## 5. Transparency

### 5.1 AI Behavior Explanation

Yami's AI agents operate under the following constraints:

- **Judge:** Read-only. Evaluates findings against OWASP skills. Emits structured JSON decisions. Never writes code.
- **Surgeon:** Edit-only (single file). Implements the Judge's `remediationIntent`. Never decides.
- **Publisher:** Git-only. Creates branches and PRs. Never merges.
- **Auditor:** Read-only. Summarizes the audit trail for human consumption.

### 5.2 Limitations

- Yami only remediates findings it can verify (Terraform, YAML workflows, supply chain pins)
- Yami does not handle runtime security (e.g., runtime threat detection)
- Yami requires a working Terraform/Checkov/Trivy environment
- Yami's AI decisions are probabilistic (confidence score < 1.0 for most cases)

### 5.3 Generated Output Labeling

All PRs created by Yami include:

```markdown
*Generated by Yami - human review required before merge.*
```

The PR body contains:
- Rule ID and resource address
- Remediation intent
- Files modified
- OWASP references
- Verification results

## 6. Model and Provider

### 6.1 Model Specification

| Attribute | Value |
|---|---|
| **Provider** | Amazon Bedrock |
| **Model** | Claude Sonnet 4.5 (`amazon-bedrock/us.anthropic.claude-sonnet-4-5-20250929-v1:0`) |
| **Temperature** | `0.0` (deterministic) |
| **Output format** | Structured JSON (JSON schema validated) |
| **Retry policy** | `retryCount: 2` for invalid JSON |
| **Timeout** | 120 seconds per invocation |

### 6.2 Credentials

| Method | Status | Scope |
|---|---|---|
| **OIDC (preferred)** | Supported | `bedrock:InvokeModel` only |
| **IAM key (fallback)** | Supported | Scoped IAM key in GitHub secret |
| **Long-lived token** | Not used | `AWS_BEARER_TOKEN_BEDROCK` exists but not primary |

**Critical:** No credentials are committed to the repository. `opencode.json` contains only the provider configuration (region). Credentials are injected via GitHub Actions environment variables.

### 6.3 Model Version Tracking

- Model version is pinned in the frontmatter of each agent (`.opencode/agents/*.md`)
- Changes to model version require updating the governance manifest (`.opencode/MANIFEST.json`)
- The manifest is chain-linked SHA-256 and verified at runtime

## 7. Monitoring

### 7.1 Operational Indicators

| Indicator | Source | Threshold |
|---|---|---|
| Token consumption | `TokenBudget.java` | Hard cap: 1,000,000 tokens/run |
| HTTP timeout | `OpenCodeClient.java` | 120 seconds |
| Agent steps | OpenCode native | `steps: N` (configurable) |
| Doom loop | OpenCode native | Blocks repeated identical tool calls |
| KillSwitch | `KillSwitch.java` | `YAMI_DISABLED=true` or programmatic trigger |

### 7.2 Quality Indicators

| Indicator | Source | Target |
|---|---|---|
| Verification pass rate | `Verifier.java` | > 95% for SAFE_FIX decisions |
| Constitutional veto rate | `PolicyEngine.java` | Tracked in audit trail |
| Human review rate | `Decision.java` | Tracked in audit trail |
| Patch deviation rate | `DeviationDiff.java` | 0% (all deviations escalated) |

### 7.3 Abuse Indicators

| Indicator | Source | Response |
|---|---|---|
| Token budget exceed | `TokenBudget.java` | KillSwitch triggers, run aborts |
| Repeated identical calls | OpenCode `doom_loop` | Blocked automatically |
| Invalid JSON responses | `OpenCodeClient.java` | Retry 2x, then HUMAN_REVIEW |

## 8. Change Management

### 8.1 Governance Artifacts

The following files are **governance artifacts**. Modifying them changes the security posture:

| Artifact | Location | Change Rule |
|---|---|---|
| Agent definitions | `.opencode/agents/*.md` | Cross-review required |
| OWASP skills | `.opencode/skills/*/` | Cross-review required |
| Policy configuration | `policies/yami.yml` | Cross-review required |
| Governance manifest | `.opencode/MANIFEST.json` | Regenerated automatically, verified by CI |

### 8.2 Manifest Verification

- `.opencode/MANIFEST.json` contains chain-linked SHA-256 hashes of all `.md` files
- Generated by `GovManifestTool.java`
- Verified by CI and at runtime by `Harness.java`
- **Any modification without regenerating breaks the build**

### 8.3 Version Control

- All governance artifacts are versioned in Git
- The manifest links each hash to a Git commit
- Audit trails reference the manifest version used for each run

## 9. Incident Response

### 9.1 Incident Types

| Type | Example | Response |
|---|---|---|
| **Unsafe AI behavior** | Surgeon writes vulnerable code that passes verification | KillSwitch → YAMI_DISABLED=true → all writes stop |
| **Compromised token** | Unauthorized PR created | KillSwitch → revoke token → investigate audit trail |
| **Model degradation** | Bedrock returns invalid JSON repeatedly | Fallback to replay mode → HUMAN_REVIEW |
| **Governance bypass** | Manifest verification fails | KillSwitch → escalate to human |
| **Supply chain attack** | Compromised tool binary | CI security scans detect it (Trivy gate) |

### 9.2 Response Playbook

1. **Detect:** KillSwitch, CI failure, or audit anomaly
2. **Contain:** `YAMI_DISABLED=true` stops all agent invocations
3. **Investigate:** Review `audit.json` artifact for full trace
4. **Escalate:** Human review with complete context
5. **Recover:** Fix root cause, reset KillSwitch, re-run

### 9.3 Audit Trail

Every run produces `audit.json` containing:
- SHA-256 hashes of findings, skills, and files (before/after)
- Exported OpenCode sessions (full agent conversations)
- Verification results
- Decision outcomes with confidence scores
- `fallbackMode` flag for degraded runs
